01 · A fonte

A API do USGS por dentro

Antes: o que é uma API

API (Application Programming Interface) é a porta que um sistema abre para outros programas conversarem com ele. Pense no balcão de um restaurante: você não entra na cozinha, faz o pedido no formato que o cardápio aceita e recebe o prato pronto. A API é o cardápio e o balcão ao mesmo tempo. Ela diz o que dá para pedir, como pedir e o que volta.

As APIs de dados que você vai encontrar no trabalho são quase todas APIs web (ou REST): o pedido é uma URL, igual à de um site, e a resposta vem em texto estruturado, quase sempre JSON. A diferença para um site é quem lê: o site devolve uma página para uma pessoa, e a API devolve dado para um programa.

Peça do pedidoNo USGSO que é
Endereço basehttps://earthquake.usgs.gov/fdsnws/event/1Onde a API mora
Endpoint/countQual pergunta você está fazendo
Parâmetros?starttime=2025-07-01&minmagnitude=2.5Os filtros, depois do ?, separados por &
Status200Um número que diz se deu certo, antes mesmo de ler a resposta
Corpo{"count": 4181, ...}A resposta em si, em JSON

Dá para testar sem código: cole esta URL no navegador e a resposta aparece na tela. O requests.get do notebook faz exatamente isso, só que de dentro do Python. Muitas APIs pedem uma chave para saber quem está chamando e limitar o uso. A do USGS é pública e não pede.

A API de eventos do USGS

A API de eventos do USGS segue o FDSN, o padrão internacional de serviços de sismologia. É uma API REST sem chave: você monta uma URL com filtros e recebe os eventos. Dos endpoints que ela oferece, o curso usa dois:

EndpointDevolvePor que usar
/count{"count": 4181, "maxAllowed": 20000}Saber quanto vai vir, antes de baixar. Responde em milissegundos.
/queryUm GeoJSON com os eventosBaixar de fato. Aceita exatamente os mesmos filtros do /count.

Os filtros que o curso usa são sempre os mesmos: format=geojson, minmagnitude=2.5, orderby=time-asc e a janela starttime / endtime. O endtime é exclusivo: julho é 2025-07-01 até 2025-08-01, sem buraco e sem sobreposição entre meses.

O limite que obriga a fatiar

O /query devolve no máximo 20.000 eventos por chamada. Acima disso, a API não corta nem pagina: responde 400 Bad Request com o motivo escrito. 2025 inteiro tem 29.265 eventos de magnitude 2,5 ou mais. Não cabe numa chamada, mas cada mês cabe com folga.

Contagens medidas em 06/11/2026. Julho tem quase o dobro dos outros meses: são as réplicas do terremoto de magnitude 8,8 em Kamchatka, no dia 29. Fatiar por mês dá folga de quase cinco vezes. Se um dia um mês passar do limite, o /count avisa antes, e o código para com erro em vez de baixar pela metade.

Pergunta para a turma: e se um mês sozinho passasse de 20 mil eventos? Um terremoto gigante gera milhares de réplicas, e julho já teve o dobro do normal. Antes de ler a resposta, pense em como você baixaria esse mês.

Paginação: o jeito comum de buscar muito dado

Quase toda API limita quanto devolve por chamada, para proteger o servidor. A saída padrão é a paginação: a resposta vem em pedaços, as páginas, e você pede uma de cada vez até acabar, como quem vira as páginas de um livro. Há dois estilos principais:

EstiloComo funcionaPonto fraco
Offset e limit"Me dê 20 mil a partir do registro 1", depois "a partir do 20.001". O USGS aceita esse estilo, com os parâmetros offset e limit.Se um registro entra ou sai entre uma página e outra, todos depois dele mudam de posição, e algum evento é pulado ou vem repetido.
Cursor ou tokenCada resposta traz um marcador, como next_page_token, que você devolve para receber a próxima página. É o estilo das APIs de Google, Stripe, GitHub e muitas outras.Só dá para andar para a frente, uma página de cada vez. Não é possível pular direto para a página 5.

No USGS, existe uma alternativa melhor que paginar: fatiar pelo tempo, que é o que o curso já faz com os meses. "De 1 a 16 de julho" sempre aponta para os mesmos eventos, enquanto "a página 2" depende do que mudou no catálogo desde a página 1. A resposta para a pergunta, então: se um mês passasse do limite, ele seria dividido ao meio, e cada metade conferida de novo no /count, até cada pedaço caber.

Esse caminho tem uma armadilha: o número de arquivos de um mês passa a depender da contagem, que muda com as revisões, e a Bronze pode receber o mesmo evento duas vezes. Não tem problema, porque a Bronze não promete unicidade. Quem promete é a Silver, com o MERGE pelo id da aula 3. Cada camada garante uma coisa.

Anatomia de uma resposta

O /query devolve um FeatureCollection: um objeto só, com um cabeçalho e uma lista de eventos. É o primeiro evento de julho de 2025, como a API manda, só que com espaçamento para ler:

{ "type": "FeatureCollection",
  "metadata": { ..., "count": 4181 },
  "features": [
    { "type": "Feature",
      "properties": {
        "mag": 4.6,
        "place": "Nicobar Islands, India region",
        "time": 1751328415616,
        "updated": 1757018407040,
        "status": "reviewed",
        "type": "earthquake",
        "magType": "mb",
        ... mais 19 campos
      },
      "geometry": { "type": "Point",
        "coordinates": [94.0027, 9.167, 10] },
      "id": "us7000qc1d"
    },
    ... mais 4.180 eventos
  ],
  "bbox": [ ... ] }
  1. metadata.count · a própria resposta diz quantos eventos tem. Serve de conferência na Bronze.
  2. time, updated · milissegundos desde 01/01/1970, em UTC. Ainda não são data: viram na aula 3.
  3. status · automatic (estimativa do computador) ou reviewed (conferido). Em 2025, 290 eventos ainda são automáticos.
  4. type · nem tudo é terremoto: há 232 explosões de mineração no ano. Decisão da Silver.
  5. coordinates · longitude, latitude e profundidade em km, nessa ordem. Longitude primeiro pega muita gente.
  6. id · a chave do evento. É por ela que o MERGE da aula 3 atualiza em vez de duplicar.

Documentação de todos os campos: ComCat event terms. Dos parâmetros: API FDSN de eventos.

Quando a API erra, e quando é você

Código de status HTTP não é detalhe: ele decide se vale a pena tentar de novo.

StatusQuer dizerO notebook faz
200Deu certoSegue
429Chamadas demais em pouco tempoEspera e tenta de novo: 1, 2, 4, 8, 16 segundos
5xxO servidor está com problemaEspera e tenta de novo, igual
400O pedido está erradoFalha na hora. Repetir o mesmo pedido dá o mesmo erro

Esperar cada vez mais entre tentativas se chama backoff exponencial. Ele dá tempo para o servidor se recuperar, em vez de martelar quem já está sobrecarregado.

02 · A primeira parada

Landing: guardar antes de entender

Daria para ler a API e gravar direto numa tabela, num passo só. O curso separa em dois de propósito, e a separação é o primeiro sinal de pipeline de pleno:

API direto para a tabela

requests → DataFrame → tabela

Se o código de carga tem um bug, você conserta e chama a API de novo. Só que a API já mudou: o USGS revisou eventos desde ontem. Não dá para reproduzir o que deu errado, nem provar o que a fonte disse.

API para a landing, depois a tabela

requests → arquivo → Auto Loader → tabela

O arquivo é a prova do que a fonte respondeu, naquele dia. A carga pode ser refeita quantas vezes for preciso sem tocar na API. Extração e carga falham, e são consertadas, separadamente.

Três regras fazem a landing funcionar:

  • Byte a byte. Grava resposta.content, e não um JSON reprocessado pelo Python. Nada de reordenar chave ou trocar número por texto: o arquivo é o que a API disse.
  • Caminho determinístico. terremotos/ano=2025/mes=07.geojson depende só da janela pedida, nunca do horário da execução. Rodar de novo sobrescreve o mesmo arquivo, então a landing tem sempre 12, e não 24.
  • Só grava o que foi conferido. Se o /count disse 4.181 e vieram 4.180, o arquivo não é gravado. Arquivo pela metade é pior que arquivo nenhum, porque parece certo.
Idempotência, de novo. Na aula 1 a palavra apareceu no vocabulário. Aqui ela vira código: o 01_extract é idempotente porque o nome do arquivo é fixo, e o 02_bronze vai ser idempotente por outro motivo, o checkpoint. Dois mecanismos diferentes, a mesma garantia: rodar uma ou dez vezes deixa o dado igual.

03 · A carga

Auto Loader e checkpoint

Arquivo em volume ainda não é tabela: não dá para fazer SELECT, não tem histórico, não tem linhagem. O passo seguinte é ler os arquivos e gravar em Delta. Existem três jeitos de fazer isso, e a diferença entre eles só aparece na segunda execução, que é exatamente a que o Job vai rodar todo dia.

Antes: como a landing se organiza em pastas

Uma landing raramente é uma pasta só com tudo dentro. O padrão é a partição por pastas (o estilo Hive): o nome de cada pasta tem o formato chave=valor, e cada pedaço do dado fica separado dos outros. A do curso separa por ano, porque é uma carga histórica. Um pipeline diário separa por dia:

A landing do curso

terremotos/
└ ano=2025/
    mes=01.geojson
    ⋮
    mes=12.geojson

Um pipeline diário típico

landing/
├ dia=2026-11-16/eventos.geojson
├ dia=2026-11-17/eventos.geojson
└ dia=2026-11-18/eventos.geojson

A partição por pastas traz duas vantagens:

  • O Spark entende a pasta como coluna. ano=2025 vira uma coluna ano na tabela, sem estar dentro do arquivo.
  • Dá para ler só um pedaço. Um filtro WHERE ano = 2025, ou um caminho apontando para uma pasta só, faz o Spark ignorar as outras pastas sem nem abrir os arquivos delas. Isso se chama partition pruning.

Por isso, num pipeline diário, a função de carga quase sempre lê só a pasta do dia: o Job passa a data como parâmetro, e o código monta o caminho landing/dia=2026-11-18/ e carrega só ela. Funciona, mas a responsabilidade de não reler e não pular fica com quem chama. Se o Job de ontem falhou, alguém tem que lembrar de rodar ontem de novo. Se o mesmo dia rodar duas vezes, duplica. Com essa organização em mente, os três jeitos de carregar:

Três jeitos de carregar

Cada quadradinho é um arquivo da landing, ou a linha que ele vira na tabela. Na 1ª execução, os três jeitos parecem iguais. Na 2ª, só o Auto Loader acerta o número sem reprocessar o que já tinha.

JeitoO que faz em cada execuçãoServe para
appendLê a pasta inteira e acrescenta tudo à tabela. Não sabe o que já gravou antes.Dado que chega sempre em arquivo novo e é lido uma vez só. Rodar duas vezes duplica.
overwriteLê a pasta inteira, apaga a tabela e grava de novo.Tabela pequena, recalculada do zero, como uma Gold. Na Bronze, joga fora o histórico e fica mais cara a cada dia.
Auto LoaderConsulta o checkpoint, lê só os arquivos novos e acrescenta só eles.Ingestão de arquivos que não param de chegar. É o que a Bronze usa.

O que o Auto Loader faz

O Auto Loader é o leitor de arquivos do Databricks (format("cloudFiles")). Ele olha a pasta, compara com uma lista de arquivos já processados, que ele guarda no checkpoint, e lê só a diferença. O checkpoint é gravado junto com a tabela, na mesma transação: ou os dois avançam, ou nenhum avança.

Um pipeline diário típico: a extração grava cada dia na sua própria pasta, e o Auto Loader lê só o que é novo. Gravar na tabela e anotar no checkpoint acontecem juntos: se a execução cair no meio, nenhum dos dois avança, e a próxima refaz o mesmo arquivo sem duplicar.

Compare com a carga que lê só a pasta do dia: o Auto Loader chega ao mesmo resultado sem receber a data. Ele lista todas as pastas, e o checkpoint descarta o que já foi lido. A pasta do dia é lida porque é a única novidade, e não porque alguém disse qual era. Se um dia falhar, a próxima execução lê os dois.

1ª execução

landing: 12 arquivos
checkpoint: vazio
→ lê 12, grava 12 linhas
→ checkpoint anota os 12

A primeira vez também infere o schema e guarda em _schema, para não adivinhar de novo.

2ª execução

landing: 12 arquivos
checkpoint: 12 já lidos
→ lê 0, grava 0 linhas
→ tabela continua com 12

Se aparecer um 13º arquivo amanhã, a execução lê só ele. É a carga incremental da aula 4, de graça.

Streaming que se comporta como batch

O Auto Loader é uma leitura em streaming (readStream). Isso assusta, mas o streaming aqui é só o mecanismo que dá memória ao leitor. Quem decide se ele fica ligado para sempre ou não é o trigger:

TriggerComportamentoNo Free Edition
availableNow=TrueProcessa tudo o que existe agora e para. Igual a um batch, com memória.Funciona. É o que o curso usa.
processingTime="1 minute"Fica ligado, olhando a pasta a cada minuto.Não suportado no serverless. E gastaria a cota.

Com availableNow, o mesmo notebook roda na mão hoje e dentro de um Job amanhã, sem mudar uma linha.

As opções, uma por uma

OpçãoPara quê
cloudFiles.formatO formato dos arquivos: json.
multiLineCada arquivo é um objeto JSON quebrado em milhares de linhas. Sem isso, o Spark lê cada linha como um registro e tudo vira _corrupt_record.
cloudFiles.inferColumnTypesSem ela, o Auto Loader grava todo campo de JSON como texto, inclusive o array features inteiro. Com ela, array continua array e número continua número.
cloudFiles.schemaLocationOnde o schema inferido fica guardado.
cloudFiles.partitionColumnsTransforma a pasta ano=2025 numa coluna ano.
checkpointLocationA memória: o que já foi gravado. Um checkpoint por tabela, nunca compartilhado.
_metadata.file_pathColuna escondida que todo arquivo lido tem. Vira _source_file, para saber de onde cada linha veio.

Repare

A versão 0 é o CREATE TABLE. As versões com operation = STREAMING UPDATE são da primeira execução: o Auto Loader pode dividir os 12 arquivos em mais de um lote (por exemplo, 10 + 2), e cada lote vira uma versão. Somadas, dão 12 linhas. A segunda execução não criou versão nova: sem arquivo novo não há o que gravar, e o Delta não registra commit vazio. O histórico igual antes e depois, com a contagem em 12, é a prova que o desafio pede.

E se o USGS revisar um evento?

Rode o 01_extract de novo e depois o 02_bronze. Também dá 0 linhas novas, mesmo que os arquivos tenham mudado por dentro. O Auto Loader reconhece arquivo pelo caminho, e um arquivo reescrito com o mesmo nome não é relido (a opção cloudFiles.allowOverwrites vem desligada).

É ótimo para não duplicar e ruim para quem quer a revisão. A solução não é ligar a opção: é a carga incremental da aula 4, em que cada execução grava um arquivo novo, só com o que mudou desde a última, usando o parâmetro updatedafter da API.

Olhar a Bronze no SQL editor

Mesma regra da aula 1: um comando por vez no SQL Editor.

Comando 1 de 4 · o schema

DESCRIBE sismos.bronze.terremotos_raw;
  • features é ARRAY<STRUCT<...>>, igual à API, com os tipos que o próprio JSON tem: mag é DOUBLE, time é BIGINT. Isso é ler o JSON direito, e não converter: time continua em milissegundos.
  • ano veio do nome da pasta. _ingested_at e _source_file são as colunas de auditoria.
  • _rescued_data foi criada sozinha: se um arquivo futuro trouxer um campo que não cabe no schema, ele vai para lá em vez de ser perdido.

Comando 2 de 4 · a resposta concorda com ela mesma?

SELECT regexp_extract(_source_file, 'mes=([0-9]+)', 1) AS mes,
       metadata.count                  AS diz_a_api,
       size(features)                  AS na_bronze,
       metadata.count = size(features) AS bate
FROM sismos.bronze.terremotos_raw
ORDER BY mes;

Doze linhas, todas com bate = true.

Comando 3 de 4 · nem todo evento é terremoto

SELECT f.properties.type AS tipo, count(*) AS eventos
FROM (SELECT explode(features) AS f FROM sismos.bronze.terremotos_raw)
GROUP BY ALL
ORDER BY eventos DESC;

O explode transforma cada elemento do array numa linha, só durante a consulta. Resultado esperado: 29.022 earthquake, 232 mining explosion e um punhado de outros (explosão, deslizamento, erupção). Ficam, saem ou ganham uma coluna? É a primeira decisão da Silver.

Comando 4 de 4 · os maiores do ano

SELECT f.id,
       f.properties.place                                  AS lugar,
       f.properties.mag                   AS magnitude,
       timestamp_millis(f.properties.time) AS horario_utc,
       f.properties.status
FROM (SELECT explode(features) AS f FROM sismos.bronze.terremotos_raw)
ORDER BY magnitude DESC
LIMIT 5;

Repare

No topo, us6000qw60, Kamchatka, 8.8 e reviewed: o mesmo evento que você inventou à mão na prática de Delta da aula 1, agora vindo da fonte. Logo abaixo, Mianmar e a Passagem de Drake. O timestamp_millis traduziu os milissegundos só nesta consulta. Na aula 3, essa conversão vai para dentro da Silver, uma vez só.

Quando quebrar

ConnectionError ou Max retries exceeded no 01_extract

É o Free Edition bloqueando o domínio, e não erro no código. Siga o plano B da aula 1: o zip com as mesmas respostas vai para a landing, e você continua a partir do 02_bronze.

A API respondeu 400 Bad Request

Leia o corpo da resposta (r.text): o USGS explica o motivo. Quase sempre é consulta grande demais (exceeds search limit of 20000) ou data em formato errado. É o caso em que repetir não adianta, e por isso o notebook falha na hora.

A API respondeu 429 ou 503 várias vezes

Chamadas demais em pouco tempo, ou servidor sobrecarregado. No serverless, a turma inteira pode estar saindo pelo mesmo endereço de rede. A nova tentativa com espera crescente resolve na maioria das vezes. Se esgotar as cinco, rode a parte 5 do 01_extract de novo daqui a alguns minutos: só os meses que faltam importam, e os que já estão na landing são sobrescritos sem dano. Não tire o time.sleep(1) para "ir mais rápido".

/count disse 4181, vieram 4180

O USGS mudou o catálogo entre as duas chamadas: um evento entrou, saiu ou foi revisado no meio. É raro, e a conferência existe exatamente para pegar isso. Rode de novo. Se repetir sempre no mesmo mês, avise no grupo.

A Bronze tem só a coluna _corrupt_record

Faltou o .option("multiLine", "true"). Corrija e recomece do zero (próximo item): o schema errado ficou guardado no _schema do checkpoint, e só corrigir o código não basta.

Cannot resolve "size(features)": features tem o tipo STRING

Faltou o .option("cloudFiles.inferColumnTypes", "true"): sem ela, o Auto Loader grava o array features inteiro como texto. Acrescente a opção e recomece do zero (próximo item). Só corrigir o código não basta, porque o schema em texto ficou guardado no _schema do checkpoint.

Preciso recomeçar a Bronze do zero

Apague a tabela e o checkpoint, juntos, numa célula Python:

spark.sql("DROP TABLE IF EXISTS sismos.bronze.terremotos_raw")
dbutils.fs.rm("/Volumes/sismos/bronze/checkpoints/terremotos_raw", recurse=True)

Apagar só um dos dois deixa o par inconsistente. Só a tabela: o checkpoint acha que já leu tudo, e nada volta para a tabela. Só o checkpoint: tudo é relido, e a tabela fica com 24 linhas.

A Bronze ficou com 24 linhas

O checkpoint foi apagado ou trocado de caminho entre duas execuções, e o Auto Loader releu tudo. Confira se o CKPT é exatamente /Volumes/sismos/bronze/checkpoints/terremotos_raw e recomece do zero (item anterior).

UnknownFieldException ou [UNKNOWN_FIELD_EXCEPTION...]

Um arquivo novo trouxe um campo que o schema guardado não tinha. O Auto Loader para de propósito, atualiza o schema no _schema e espera você rodar de novo. Rode a célula do Auto Loader mais uma vez: da segunda vez passa, com a coluna nova.

A computação desligou e não volta

Você passou da cota diária do Free Edition. A computação volta no dia seguinte, e nada se perde: tabelas, volumes, checkpoint e notebooks continuam lá. Quando voltar, rodar o 02_bronze de novo continua de onde parou.
