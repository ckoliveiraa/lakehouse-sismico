O EMSC tem quase o triplo. A pergunta certa não é "qual está certo", e sim "certo para quê". Casar os dois catálogos evento a evento é o desafio 3.

A armadilha do checkpoint

O checkpoint é a memória de uma consulta de streaming: quais arquivos ela já viu e com que schema. Testado no Free Edition: a carga do EMSC com um checkpoint novo funciona. Depois, a carga do USGS com o mesmo checkpoint falha com LOCATION_OVERLAP, e o arquivo citado no erro é emsc/ano=2025/mes=11.geojson, e não um do USGS. A consulta nova herdou a memória da outra fonte. Fora do Unity Catalog, isso pode passar calado: arquivo tratado como já lido, schema de uma fonte aplicado à outra. E não tem conserto fino: só apagando o checkpoint, o que obriga a reprocessar tudo.

Por isso o bronze_ingestao não deixa ninguém escolher o checkpoint. Landing e checkpoint saem do mesmo par <tópico>/<fonte>, e a tabela, de <fonte>_raw:

checkpointcheckpoints/terremotos/usgscheckpoints/terremotos/emsc

E na Silver? O notebook continua um só, com fonte como parâmetro, mas a tradução muda de lado: cada fonte tem nomes de campo e formatos de data próprios, e conciliar isso é justamente o trabalho da Silver. Uma função de tradução por fonte, e as duas chegam ao mesmo contrato de colunas, na mesma tabela. É a seção 03.

02 · O workspace como código

Bundles e CLI: a porta para agentes

Até aqui, tudo foi clicado: importar notebook, criar Job, trocar widget, apertar Run all. Clique não tem histórico, não passa por revisão e não se repete igual no workspace do colega. E tem um motivo novo: agente não clica bem. Um agente de código, como o Claude Code, o Cursor ou o Copilot, trabalha pelo terminal: lê arquivos, roda comandos, lê o erro e tenta de novo. Para ele operar o Databricks, o Databricks precisa caber num terminal.

Databricks CLI

databricks <comando> -p <perfil>

A API inteira do workspace no terminal: tabelas, volumes, jobs, SQL. A autenticação fica num perfil em ~/.databrickscfg, e o token nunca aparece no código nem no prompt do agente.

Bundle

databricks.yml → validate → deploy → run

Um arquivo YAML no repositório descreve o que existe no workspace: Jobs, tasks, parâmetros e notebooks. O deploy faz o workspace ficar igual ao arquivo, e rodar de novo não duplica nada.

O Job do projeto é este arquivo na raiz do repositório. Abaixo, a parte da Bronze. Repare: duas tasks, o mesmo notebook, e só o parâmetro fonte muda. O arquivo completo tem mais três tasks, Silver do USGS, Silver do EMSC e Gold, que são as próximas seções da aula.

bundle:
  name: lakehouse-sismico

resources:
  jobs:
    pipeline_terremotos:
      name: pipeline_terremotos
      parameters:
        - name: ano
          default: "2025"
        - name: extrair
          default: "sim"
      tasks:
        - task_key: bronze_usgs
          notebook_task:
            notebook_path: ./notebooks/bronze_ingestao.py
            base_parameters: { fonte: usgs }
        - task_key: bronze_emsc
          notebook_task:
            notebook_path: ./notebooks/bronze_ingestao.py
            base_parameters: { fonte: emsc }
        # silver_usgs, silver_emsc e gold: seções 03 a 05

targets:
  dev:
    mode: development
    default: true

Sem cluster declarado, as tasks rodam em serverless, que é o que o Free Edition oferece. O mode: development põe o prefixo [dev seu_nome] no Job e isola o deploy na sua pasta, para dois alunos não pisarem um no outro. O host do workspace não está no arquivo: vem do perfil (-p), e o repositório pode ser público.

Por que isso é a conexão com agentes

  • Mesmos comandos, mesmo resultado. O que você roda no terminal, o agente roda igual. Não tem tela que mudou de lugar.
  • Erro legível. bundle validate e a saída do run são texto: o agente lê, corrige o YAML ou o notebook e roda de novo.
  • Revisável. O agente muda o databricks.yml e o notebook no git. Você lê o diff antes do deploy.
  • Com limite. O agente herda as permissões do perfil que ele usa. Em dev, é você. Em produção, é uma service principal com só o necessário: assunto da aula 4.

03 · A camada do meio

O que a Silver promete

Cada camada garante uma coisa diferente. A Bronze garante fidelidade: é o que a fonte disse, sem retoque. A Gold garante resposta: uma pergunta de negócio, pronta para consultar. A Silver fica no meio e garante que o dado está limpo e confiável, sem ainda saber que pergunta vão fazer a ele. Na prática, são quatro promessas:

1 · GRÃO

Uma linha por evento

O array features vira linhas. A chave é o par (fonte, id): cada catálogo tem o seu id.

2 · TIPO

Nomes, tipos e unidades escolhidos

Milissegundos do USGS e texto ISO do EMSC viram o mesmo TIMESTAMP em UTC. As duas fontes, um contrato só.

3 · ESCOPO

Uma decisão escrita sobre o que fica

Explosão de mina fica, sai ou ganha coluna? Com o número de linhas antes e depois.

4 · VERSÃO

Só a revisão mais nova

MERGE por (fonte, id): evento novo entra, revisão nova atualiza, versão velha é ignorada.

Grão: explodir o array

Grão é a resposta para "o que é uma linha desta tabela?". Na Bronze, uma linha é uma resposta da API, e julho inteiro mora numa célula só. Para contar, filtrar ou juntar eventos, o grão precisa ser o evento. A função explode faz essa troca: recebe um array e devolve uma linha para cada elemento, repetindo as outras colunas que você levar junto.

A linha de julho vira 4.181. As doze linhas da Bronze viram 29.265, e a soma tem que bater com o sum(size(features)) da aula 2.

Tipo: cada coluna é uma decisão

O Auto Loader leu a Bronze com inferColumnTypes: ele olhou o JSON e adivinhou os tipos. Funciona, mas o palpite muda se o dado mudar. Se um dia o USGS mandar a magnitude 5 em vez de 5.0, o palpite pode mudar junto. A Silver não fica à mercê disso: ela declara o schema num CREATE TABLE e converte cada campo explicitamente. É o contrato da camada, e quem consome sabe o que esperar.

Duas fontes, um contrato

A tabela acima é a tradução do USGS. O EMSC chega na mesma tabela, com as mesmas colunas, mas cada uma vem de outro lugar e às vezes em outro formato. O notebook tem uma função por fonte, normalizar_usgs e normalizar_emsc, e o resto do código (escopo, deduplicação, MERGE, conferências) é um só. No fim da tradução, um select(*COLUNAS) com as colunas lidas da própria tabela garante o contrato: se uma função esquecer uma coluna, o erro aparece ali, e não no MERGE.

A Silver guarda tudo o que a fonte disse, limpo. Cada Gold filtra o que a sua pergunta pede, e o filtro fica escrito na consulta, à vista de quem lê. É a decisão do curso.

No EMSC, a mesma decisão vale para 114 eventos de 79.492: 77 emsc:se (suspeitos), 35 emsc:ue (sem confirmação) e 2 emsc:si (suspeita de induzido). Ficam na Silver, fora da Gold.

A regra que sobra: decisão de escopo é escrita, com o número de linhas que ela afeta. "Mantivemos os 243 eventos que não são terremoto, com a coluna tipo, e a Gold filtra" é uma frase que alguém consegue questionar na revisão de código. Um WHERE perdido no meio do notebook, não.

Olhe o dado antes de escrever a regra. Uma validação "profundidade não pode ser negativa" parece óbvia. Só que 44 eventos do USGS em 2025 têm profundidade negativa, e 31 do EMSC, e não é erro: o USGS mede a partir do nível do mar, e um tremor sob uma montanha pode estar acima dele. A regra óbvia jogaria fora dado bom. O 03_silver mostra esses eventos na parte 3.

04 · A versão

MERGE: atualizar sem duplicar

As fontes revisam os eventos depois de publicar. Um terremoto entra como automatic, com a estimativa do computador, e dias depois um sismólogo confere e corrige a magnitude, a profundidade, às vezes o lugar. O id continua o mesmo, o updated muda. A Silver precisa refletir isso: cada evento uma vez, na revisão mais nova.

Os dois jeitos de gravar da aula 2 não servem. O append duplica o evento a cada revisão. O overwrite recalcula tudo, todo dia, a partir da Bronze inteira, e uma versão velha relida da landing apaga a nova. O que resolve é o upsert: atualizar o que existe, inserir o que não existe. No SQL, isso se chama MERGE.

Uma instrução, três casos. O terceiro é o que acontece com quase todos os 108 mil eventos todo dia, e é ele que faz a segunda execução não mexer em nada.

Anatomia do MERGE

MERGE INTO sismos.silver.eventos AS t
USING origem AS s
ON t.fonte = s.fonte AND t.id = s.id
WHEN MATCHED
  AND s.atualizado_em > t.atualizado_em
  THEN UPDATE SET *
WHEN NOT MATCHED
  THEN INSERT *
  1. t e s · o alvo (target, a Silver) e a origem (source, a Bronze explodida e tipada, registrada como view temporária).
  2. ON · a chave, (fonte, id). Diz quando uma linha da origem "é a mesma" que uma da Silver. Sem a fonte, um id do EMSC que por acaso coincidisse com um do USGS sobrescreveria o evento errado. O notebook ainda acrescenta t.fonte = 'usgs' (ou 'emsc'): não muda o resultado, mas diz ao Delta que a execução só toca as linhas de uma fonte.
  3. AND ... · a condição que protege a Silver. Sem ela, todo MERGE reescreveria todas as linhas da fonte, mesmo sem nada ter mudado, e uma versão velha da landing sobrescreveria a revisão nova.
  4. SET *, INSERT * · todas as colunas, casadas pelo nome. A origem precisa ter exatamente as colunas da tabela.

Uma linha por (fonte, id), antes de casar

O MERGE tem uma exigência: cada linha da Silver pode casar com no máximo uma linha da origem. Se o mesmo id vier duas vezes, ele não escolhe sozinho e falha com DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE.

Hoje a Bronze não tem id repetido. Na aula 4 vai ter: cada carga incremental grava um arquivo novo só com o que mudou, e um evento revisado duas vezes aparece em dois arquivos. Por isso o notebook já resolve antes de precisar, com uma função de janela: numera as versões de cada id da mais nova para a mais velha e fica com a número 1.

mais_nova = (Window.partitionBy("fonte", "id")
                   .orderBy(F.col("atualizado_em").desc(), ...))

origem = (eventos
          .withColumn("_ordem", F.row_number().over(mais_nova))
          .where("_ordem = 1")
          .drop("_ordem"))

Aqui, recalcular tudo é a escolha certa

Na Bronze e na Silver, o curso fez de tudo para não reprocessar. Na Gold, as tabelas são recriadas inteiras a cada execução, com CREATE OR REPLACE TABLE ... AS SELECT. Não é contradição: a Gold é pequena, dezenas de linhas, e derivada, porque tudo o que ela tem dá para refazer a partir da Silver em segundos. Na Bronze, o overwrite jogaria fora o histórico da fonte. Aqui, não há nada a perder, e o Delta ainda guarda as versões anteriores. O CREATE OR REPLACE também é melhor que DROP e CREATE: a tabela nunca deixa de existir no meio, e quem consulta durante a troca vê a versão anterior inteira.

Duas fontes na Gold: lado a lado, nunca somadas

A fonte entra no GROUP BY e vira coluna da Gold. Somar USGS e EMSC daria um número sem sentido: o terremoto de Kamchatka está nos dois catálogos e seria contado duas vezes. A Gold guarda uma linha por mês e fonte, o formato certo para guardar. Para ler, um analista quer as fontes em colunas, e o FILTER (WHERE ...) faz isso sem PIVOT:

SELECT mes,
       sum(terremotos) FILTER (WHERE fonte = 'usgs') AS usgs,
       sum(terremotos) FILTER (WHERE fonte = 'emsc') AS emsc
FROM sismos.gold.terremotos_por_mes
GROUP BY mes

E aí aparece a lição que a aula 2 só tinha sugerido. No total, o EMSC vê quase o triplo: 79 mil contra 29 mil. Na magnitude 5 ou mais, os dois ficam perto, uns 2.100 cada no ano. Terremoto grande, a rede global inteira vê. Terremoto pequeno, só quem tem sismógrafo perto, e o EMSC recebe as redes regionais da Europa, do Mediterrâneo e da Indonésia. Contar terremoto pequeno mede onde há sismógrafo, e não onde o chão treme. É o viés de detecção, e o desafio 3 vai medi-lo grau a grau.

Isso é o trabalho de pleno. "Quantos terremotos teve em julho?" tem duas respostas certas, 4.159 e 7.000, e as duas consultas rodam sem erro. Saber qual usar depende da pergunta, e o COMMENT da tabela é onde se escreve isso: "não some as fontes".

Por que tabela, e não view?

Uma VIEW guarda só a consulta: cada SELECT nela recalcula o GROUP BY sobre a Silver. Está sempre atualizada, mas quem paga o cálculo é quem lê, toda vez. Uma tabela guarda o resultado: a leitura é instantânea, mas ela só muda quando alguém roda o 04_gold. Para uma Gold lida por um painel várias vezes ao dia e atualizada uma vez, de madrugada, tabela é a escolha. Quem roda o 04_gold todo dia é o Job da aula 4.

A1 · Anexo

Quando quebrar

LOCATION_OVERLAP no Auto Loader do bronze_ingestao

O checkpoint em uso já tem memória de outra origem: uma fonte reaproveitou o checkpoint de outra, ou a landing mudou de pasta e o checkpoint antigo ficou. Rode a célula de migração do passo 01, que apaga tabela e checkpoint juntos, e carregue de novo.

refresh token is invalid ou Not Found na CLI

O primeiro é login vencido: databricks auth login --profile lakehouse de novo. O segundo, no Git Bash do Windows, é o caminho /Users/... ou /api/... convertido para C:/Program Files/Git/...: prefixe o comando com MSYS_NO_PATHCONV=1.

ConcurrentAppendException no MERGE da Silver

Dois MERGE rodaram ao mesmo tempo na silver.eventos: duas abas do notebook, uma com cada fonte, ou o Job rodando enquanto você testava. Rode de novo, uma fonte de cada vez. O MERGE é atômico: o que falhou não gravou nada pela metade.

DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE

O mesmo (fonte, id) veio mais de uma vez na origem do MERGE. Confira se a parte 4 rodou e se a função recebeu o origem (deduplicado), e não o eventos.

UNRESOLVED_COLUMN ou cannot resolve no UPDATE SET *

SET * e INSERT * casam colunas pelo nome. Uma coluna da tabela não existe na origem, ou está com outro nome. Compare o DESCRIBE sismos.silver.eventos com o origem.columns. Se você mudou o CREATE TABLE depois de criar a tabela, o IF NOT EXISTS não aplicou a mudança: apague a tabela e rode a parte 0 de novo. É o caso de quem criou a silver.eventos antes de ela ganhar a coluna fonte.

O table_changes falhou dizendo que o Change Data Feed não está habilitado

A tabela foi criada antes, sem o TBLPROPERTIES. Ligue com ALTER TABLE sismos.silver.eventos SET TBLPROPERTIES (delta.enableChangeDataFeed = true) e simule a revisão de novo: o feed registra só o que mudar depois de ligado.

Kamchatka ficou com magnitude 8,9

A simulação rodou e o RESTORE não. Rode a parte 8. Se a variável versao_antes se perdeu, ache no DESCRIBE HISTORY a versão anterior ao MERGE com 1 linha atualizada e use o número dela no RESTORE TABLE ... TO VERSION AS OF.

O CREATE TABLE da Silver reclamou do PRIMARY KEY

A chave é informativa e nada no curso depende dela. Apague a linha CONSTRAINT eventos_pk PRIMARY KEY (fonte, id) (e a vírgula da linha anterior) e rode de novo.

Uma Gold veio vazia

Quase sempre é o filtro: tipo = 'Earthquake', com maiúscula, não casa com nada, porque comparação de texto diferencia maiúsculas. O valor certo é earthquake. A conferência da parte 3 existe para pegar isso: uma fonte com zero denuncia a tabela.

A Gold só tem uma fonte

A Silver só tem uma. O 03_silver roda uma fonte por vez: troque o widget para emsc e rode de novo (passo 06), depois o 04_gold.

As Gold somam menos que a Silver

Alguma linha ficou de fora do GROUP BY, por exemplo com evento_em nulo. Rode SELECT count_if(evento_em IS NULL) FROM sismos.silver.eventos. Esperado: zero. Se não for, a parte 2 do 03_silver foi alterada.

Quero refazer a Silver do zero

A Silver não tem checkpoint: é derivada da Bronze inteira a cada execução. DROP TABLE sismos.silver.eventos e rode o 03_silver de novo, uma vez com cada fonte. As Gold se refazem rodando o 04_gold.

A computação desligou e não volta

Cota diária do Free Edition. Volta no dia seguinte, e nada se perde: o MERGE e o CREATE OR REPLACE são atômicos, então uma execução interrompida não deixa tabela pela metade.
